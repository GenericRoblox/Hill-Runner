# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A 2D physics-based driving platformer ("Hill Climb"-style) built to `SPEC.md`. Plain HTML5/Canvas + vanilla JS ES modules, no build step, no npm. Physics is Matter.js v0.19.0, vendored at `lib/matter.min.js` and loaded as a classic script before the module entry point (exposes global `Matter`).

Scope: Worlds 1–6 (Farm, Town, City, Mines, Castle, Factory) fully playable, 10 levels each; each world unlocks by starring the previous world's final level. Turbo/Gems/ghost-mode/gamepad are deliberate v1 omissions per spec stretch goals.

Look: cartoon UI. Menus are DOM styled by `style.css` (Beachday display font + Fredoka rounded body font, both self-hosted in `font/` — no CDN requests; Fredoka is OFL, license alongside it; note Fredoka has NO ★/☆ glyphs, which is why rating stars are inline SVG via `starIcon()` in ScreenManager.js — never render stars as text), wood/grass boards, toy-block buttons, and a light motion layer (staggered card pop-in, panel bounce, star pop, coin count-up, win confetti — all zeroed by `prefers-reduced-motion`; the result stars use a transition-on-class-add rather than a delayed fill-both animation so a stalled animation clock can never strand them invisible); in-game terrain and most obstacles are filled with tinted tile patterns from `textures/` via `src/ui/Textures.js` (`texPattern(name, multiplyTint, tileSizePx, desat)` — returns null until loaded, callers keep a flat-color fallback; `desat` grayscales before tinting, how the teal `liquid` tile becomes water/lava/acid). Patterns anchor to the current canvas transform — fill MOVING bodies (press blocks, planks, boulders) in translated local coordinates or the texture scrolls through them instead of riding along, and fills made inside a ROTATED context must use `texUpright(name, tint, size, angleRad, desat)` (counter-rotates the tile grid so textures stay upright on screen; plain `texPattern` resets the shared pattern to upright). Per-world fills come from the `tex` entry in `WORLDS`. Backgrounds (sky, parallax, cave ceiling) stay untextured by design. Tiles are seamless and baked whole (no cropping); `Textures.js` loads every one as `<name>-texture.jpg`. Keep it that way — `stone` used to ship as a 2.9 MB PNG, a third of the game's entire download for one opaque tile with no transparency to protect, and re-encoding it at quality 95 with no chroma subsampling made it 125 KB at under one brightness level of difference per pixel.

## Commands

```powershell
# Run — serve statically from the project root (ES modules won't load via file://)
python -m http.server 8000        # then open http://localhost:8000
.\tools\serve.ps1                 # ...or this: serves + opens the browser
.\tools\serve.ps1 -Build poki     # same, for a portal build folder

# Portal builds -> builds\crazygames + builds\poki (add -Zip for upload archives)
.\tools\build-platforms.ps1 -Zip

# Physics regression test: a bot drives every level of every world headlessly.
# With the server running, open /test-sim.html in a browser, or headless.
# Levels run long now, so give it a big virtual-time budget (~10 min wall clock):
& "${env:ProgramFiles(x86)}\Microsoft\Edge\Application\msedge.exe" --headless=new --disable-gpu `
  --virtual-time-budget=6000000 --dump-dom "http://localhost:8000/test-sim.html"

# ...or ONE world, which is what you actually want while tuning a level:
#   /test-world.html?w=5&t=tier3,maxed&lv=3,4      (w=1..6, lv is 1-based, omit for all 10)
```

Debug helpers: `/debug-sim.html?world=4&level=9&tier=t3&from=6` traces one bot run (x/y/vx/vy/grounded per 0.1 s — the fastest way to diagnose a failing level). The game itself takes dev deep-links: `index.html?screen=garage`, or `?world=4&level=2&bot=1&warp=7` (bot holds gas, warp fast-forwards ~7 s — good for `--screenshot` visual checks); add `&veh=sports` to override the vehicle and `&tiers=e,s,t,b` to force its upgrade tiers (e.g. tire-look visuals).

There is no Node.js on this machine — verify JS through the browser (headless Edge as above). No linter or unit-test framework; `test-sim.html` is the test suite. The bot itself lives in `test-simbot.js` (shared by `test-sim.html` and `test-world.html`); it is kept OUT of `src/` on purpose, because `tools/build-platforms.ps1` ships `src/` wholesale. On a failure the bot reports **where and on what**: `<- at x=13976 near pit(400px)@13672` — use that instead of bisecting a 30,000 px level by hand.

**Reading sim results:** rows are prefixed F (Farm) / T (Town) / C (City) / M (Mines) / K (Castle/keep) / X (Factory) with the vehicle/tier in brackets. The campaign is **upgrade-gated by design** — several rows are *supposed* to be red.

Expected green (107 of 115 runs): every world passes all 10 levels at its intended tier — Farm at stock through F6, Town at tier 1, City at tier 3, Mines/Castle/Factory at tier 3 AND maxed. Expected RED, and load-bearing (if these start passing, the difficulty curve has gone soft):

- **F7 / F9 / F10 at stock** — the Farm's ramp gaps grow past 400 px, which a stock engine cannot carry. This is the "go buy the 1000-coin engine" moment, and Farm 1-6 pay enough at three stars to fund it.
- **F10 at tier 1** — its widest gaps want tier 2.
- **C9 / C10 at tier 2** — the City's back half wants tier 3.

Known noise (bot-only; a human reads the hazard and recovers): F8 t2 and T8 t1 flip on a landing the next tier rides out. Maxed runs are flakier than tier 3 in general — the extra speed changes every landing, and a very fast car can float off a launch lip and drop into the pit it was aimed over.

The bot is deliberately naive, so its results are a *lower bound* on playability: a level the bot wins is beatable; one it fails may still be fine for humans — but a level failing at ALL its expected tiers deserves a debug-sim trace (`/debug-sim.html?world=5&level=2&tier=max&from=8` dumps x/y/vx/vy/grounded per 0.1 s, and it is the ONLY way to find out what the car is actually doing; it is how the spike-strip placement rule below was found). Rerun after touching physics constants, vehicle stats, level geometry, or obstacles.

## Architecture

**Data-driven core** — `src/data/` defines everything gameplay-numeric:
- `vehicles.js`: roster + 4 linear upgrade tiers per stat (engine/suspension/tires/brakes), resolved by `getStatsAtTiers()` into the flat stat block `Car` consumes
- `levels.js`: all six worlds, 10 levels each, authored via the chainable `LevelBuilder` (y is down; ground baseline y=600; terrain = arrays of point "chains"; `gap()` breaks the chain to create a pit; `pothole()` is a sharp terrain notch; `roof(w)` is a `flat(w)` that also records a building span in `level.buildings`, which `GameScreen._drawBuildings` renders as a facade — cornice, walls, windows — beneath the rooftop). Terrain SHAPE helpers give each world its own ground: `waves()` (rolling country, varied crest/wavelength pairs, optional drift — Farm/Mines/Town), `basin()`/`mesa()` (landforms, not bumps), `terrace()`/`steps()` (flat shelves joined by cut ramps — City/Castle/Factory). All of them cap their own grades under the ~40° friction limit; `waves` documents `h <= 0.19 * w`, `basin`/`mesa` `d <= 0.18 * w`. `finish()` derives `deathY` from the DEEPEST authored terrain point (+550) unless the level names one — assuming a fixed depth below the START height silently breaks long levels, because sections that descend stack up until the road itself sits below the kill line and the car "falls" while driving on solid ground.
  - **Levels are composed from a SECTION LIBRARY, not written point by point.** Each section (`jumpEdge`, `jumpGap`, `jumpRamp`, `holeWall`, `pocket`, `mudHole`, `seesawSpan`, `ropeSpan`, `fenceHop`, `treeLine`, `bumpRow`, `potholeRun`, `rooftops`, `underpass`, `dipUnderpass`, `slick`, `ballYard`, `pressBay`, `fanGap`, `canal`, `craneUp`, `rockChute`, `plankSpan`, `pool`, `iceRun`, `needle`, `tireBasin`, `fireMoat`, `spikeRamp`, `barricade`, `archerWall`, `flailPost`, `compactorBay`, `beltRun`, `scrapChute`, `pipeRun`, `sludgePit`, `springLaunch`, `bladePost`, `shaftDown`) lays its OWN approach and recovery ground to the spacing rules below, and starts and ends on flat ground at the cursor. So a level built from sections cannot violate a spacing rule by accident, and fixing a section fixes every level that uses it. The `lead` flat in front of a jump or a timing hazard is load-bearing, never padding: rolling ground costs several px/step, and a lip taken off a wave crest is the difference between clearing a gap and landing in it. Jump sections also `regain()` their own height — every pit lands you lower than you left, and fifteen jumps of that puts the road 2,000 px below where it started.
  - **Paired sections** put two of a kind inside one safe envelope, deliberately set against each other: `pressPair` / `compactorPair` (different periods, so the rhythm you just solved tells you nothing about the next), `ballPair` (a long slow chain and a short fast one), `bladePair`, plus cross-hazard pairs `beltCompactor` (a belt feeding you under the ram while you try to brake), `slickPress` (a boost delivered exactly when you wanted to slow), and `rampTree` (a kicker aimed at a low branch — take it flat out and the canopy swallows you). A row of identical hazards is one puzzle repeated; two that beat against each other is a new puzzle every cycle. Spacing inside a pair still respects the braking rules — each half gets room to stop short of it.
  - **Terrain-as-hazard sections** make the ground do an obstacle's job: `dipUnderpass` (the shed sunk in a hollow, so the far bank tries to pop you into the header), `spikeLeap` (a dip that eats exactly the speed the launch past it needs), `iceLeap` (ice ON a descent running to the lip — no brakes, no throttle, the run-in decides everything), `bumpCrest` (a bump row over a rise, where the car is lightest and they hit hardest).
  - Obstacle set-pieces (`ramp()`, `seesaw()`, `ropeBridge()`, `mudDip()`, `speedBumps()`, `tree()`, `lowBeam()`, the City set: `oilSlick()`, `wreckingBall()`, `press()`, `fan()`, `water()`, `craneLift()`, the Mines set: `rockfallPit()`, `crumbleBridge()`, `moltenPit()`, `icePatch()`, `jumpHole()`, `tireStack()`, the Castle set: `fireballPit()`, `spikeStrip()`, `beam()`, `arrowVolley()`, `spikyBall()`, and the Factory set: `compactor()`, `conveyor()`, `fallingScrap()`, `pipeStart()`/`pipeEnd()`, `sludgeVat()`, `spring()`, `spinBlade()`, `elevatorDown()`) register defs that `physics/Obstacles.js` turns into bodies per run — ramps/seesaws/bumps/oil slicks/presses/tire stacks/spike strips/beams/arrow volleys need flat ground laid beneath them, `ropeBridge()`/`water()`/`craneLift()`/`rockfallPit()`/`crumbleBridge()`/`moltenPit()`/`fireballPit()`/`jumpHole()`/`fallingScrap()`/`elevatorDown()` cut their own pits, `tree()` trunks are background art with a sensor canopy overhead. `craneLift()` also drops a far-shaft wall so the car stays aboard; press blocks, lift platforms, rockfall boulders, fireballs, arrows, wrecking balls and crumble-plank releases are driven from a Matter `beforeUpdate` hook inside `Obstacles` (works in game and test-sim alike; lifts rise only while ridden, via `plugin.lastRider`; crumble planks go dynamic ~0.45 s after `plugin.lastRider` is first stamped; rockfall boulders, scrap and fireballs cycle parked → in flight → reparked on `period`/`phase`)
- `economy.js`: star and payout rules. Beating your own star record is what a level really pays for; a replay that only matches it pays a **token ~12% of base** instead. Both halves of that matter: full price for a repeat turns the easiest early level into a coin farm, but paying literally NOTHING is worse — target times are generous, so most first clears are already three stars, which would make a level pay exactly once ever and leave replays pointless. That reads as a bug, and was reported as one. Base payouts run ~35% below the pre-tuning values, EXCEPT Farm 1-3, which are left rich on purpose: the player has to reach the 1000-coin engine quickly or the opening drags before the first upgrade lands.

Adding a level or vehicle is data-only; adding a world means a new `WORLDS` entry with `playable: true` (plus `sky`/`groundColor`/`grassColor`/`parallax`/`tex`; `cave: true` draws the screen-space tunnel-roof backdrop in `GameScreen._drawCaveCeiling`).

**In-level feel layer (GameScreen, render-only — never touches physics):** the terrain is drawn with flat "diorama aprons" extending 2600 px past both ends of the playfield (synthesized per frame in `_drawTerrain`, because infinite mode's chain list is live); drifting flat-bottomed clouds fill open daytime skies (`_drawClouds`, gated off for cave/factory/castle worlds); the finish flag waves; hard landings kick a dust poof (`ParticleSystem.emitLandingDust`); and full airborne rotations raise a world-space "Flip!" popup (`_popup`/`_drawPopups`, aged in `_updateFx` alongside particles — InfiniteGameScreen's popup shows the coins the flip banked, since flips pay out there).

**Screens** — `src/core/ScreenManager.js` swaps screen objects (`enter/exit/update/render`) via `screens.show(name, params)`. Menus (Home, WorldSelect, LevelSelect, Garage, Upgrade, CustomLevels) are DOM built into `#menu-root` with the `el()` helper; screens that render to canvas (`GameScreen`, `EditorScreen`) declare `usesCanvas: true`, which is what toggles the canvas/menu-root visibility and gates `screens.render` in `main.js`. `InputManager` unifies keyboard + multi-touch into a single Gas/Brake state.

**First launch goes straight into Farm 1.** A brand-new profile (`saveData.isFirstRun()`, backed by the `firstRunDone` flag) skips Home entirely and `main.js` shows `game` at world 1 level 0 — portals, CrazyGames' quality bar in particular, want a new player driving within seconds of the page loading rather than reading a menu. The flag is set BEFORE the jump, so refreshing mid-level doesn't relaunch them into it, and an explicit `?screen=` deep link always wins (which is what keeps the editor test pages working). A returning player lands on Home as before.

**First-run onboarding** (`src/ui/Onboarding.js`, styled `.coach` in style.css) — a strip at the FOOT of the screen on the level a new player is dropped into. It is not a modal and never takes the wheel: the car is live from frame one, and the strip only comments on what the player does. The idea it is built on is that the hint MIRRORS the controls rather than describing them — each half drops onto its edge and lights up (green `--go` / red `--red`) exactly as that control is pressed, using the same toy-block press as every button in the UI. A diagram has to be believed; a mirror is verified the instant you touch a key, which is why two words of copy replace a sentence. Two beats in the one slot — controls, then "Reach the flag" — and it retires itself after 0.8 s of cumulative throttle, because that IS the proof it was understood. Constraints, both load-bearing: the board is `pointer-events: none` so the very first tap reaches the throttle (only "Got it" opts back in), and every stage runs off a TIMER, never `animationend` — `prefers-reduced-motion` kills animations outright and a card waiting on an event that never fires would sit there for the whole run. It ticks on `setInterval`, NOT rAF, because rAF never fires under `--dump-dom` and that would put the whole thing beyond `test-onboarding.html`. Gated by the `coachDone` save flag (separate from `firstRunDone`, which is already set before the first level loads).

**Controls follow the portals' restricted-key rules.** Bindings key off `event.code` (physical position), not `event.key`, so an AZERTY keyboard's ZQSD lands on the same physical keys as WASD without the player rebinding anything. **Escape is deliberately not a pause key** anywhere in the game — on the web Escape leaves fullscreen, so binding it means one press does two things and the player loses the fullscreen they chose; pause is P plus the on-screen button, and in the editor Escape backs out of modals/panels but never exits the screen. Touch pedals are drawn from the first frame on coarse-pointer devices (`coarsePointer()`), not after the first touch — waiting handed a new phone player a car and no visible controls.

**Level intro card** (`showLevelIntro()` in ScreenManager.js) — a roadside route marker naming the level: number on an amber shield, `WORLD · LEVEL N` eyebrow, the level's own title in Beachday. Fired from `GameScreen.enter()` only, never from `restart()` — a retry isn't a new place, and a card on every restart of a hard level is noise. It matters most on that first launch, where the player lands mid-hillside with nothing behind them to say where they are. Two constraints in the implementation: it is `pointer-events: none` (the very first tap has to reach the throttle), and it removes itself on a TIMER rather than on `animationend`, because `prefers-reduced-motion` kills animations outright and a card waiting for an event that never fires would sit there for the whole run. The daily-bonus toast is delayed past it — both sit top-centre.

**Menu structure & endgame reveals** — Home is deliberately two big front-door actions (`bigButton()` in HomeScreen: **Play** → WorldSelect, **Garage**) plus the mute toggle; Infinite and Created Levels are NOT on Home. WorldSelect shows the six world cards, then a `.section-head` "Extra Modes" divider, then two gated cards: **Infinite** (`isInfiniteModeUnlocked()` = every level ≥1★) and **Created Levels** (`isCreatorUnlocked()` = every level 3★). Each card renders unlocked only once `qualifies && *Seen` (the `infiniteSeen`/`creatorSeen` save flags); the first time a mode qualifies-but-unseen, WorldSelect.enter() fires `playUnlockCutscene()` (`src/ui/Cutscene.js` — a dim overlay with confetti, a lock-shatter reveal per mode, and a Continue button), marks the flag(s) seen, then re-renders with the card(s) unlocked. Beating the final campaign level (`isFinalCampaignLevel()` in levels.js) that newly unlocks a mode routes there with fanfare: GameScreen `_win()` passes `hideRetry` + `unlockMode` + `quitLabel: 'Unlock New Mode'` to `showResult`, and that exit quits to `worldselect` where the cutscene plays. LevelSelect draws a themed, **live-canvas** backdrop behind the cards per world (`WorldScene` in `src/ui/MenuScenes.js`): a compact level authored with the real `LevelBuilder` (a few of that world's signature set-pieces on flat textured ground) and painted every frame by `LevelSelect.update()` with the game's own terrain textures (`texPattern`) + the real `physics/Obstacles` set-piece renderer, stepping a parked `PhysicsWorld` so the movers (wrecking balls, presses, compactors, fireballs, rockfalls) animate exactly as in-game — no faked CSS shapes. It's a fixed full-bleed `<canvas class="world-scene">` at z-index 0 under a `.screen-content` layer, with `#menu-root:has(.world-scene)` hiding the default grass; it needs the `Matter` global, is destroyed in `LevelSelect.exit()` (frees the physics world + resize listener), and renders a single settled frame under prefers-reduced-motion. The two Extra Modes cards use a centered flex row (`.grid.extras`) so they read large, not stranded small in the auto-fill worlds grid.

**Level creator** — `src/data/customLevels.js` + `src/screens/EditorScreen.js` + `src/screens/CustomLevelsScreen.js` ("Created Levels" card in the WorldSelect **Extra Modes** section — the concrete slab among the wooden boards; there is no Home shortcut). It's the deepest ENDGAME reward: `saveData.isCreatorUnlocked()` requires **3 stars on every level of every playable world** (`everyLevelHasStars(3)`) and gates the card — locked/grayed with an unlock hint until then, then revealed once by the `playUnlockCutscene` reveal. Deep links (`?screen=editor`/`customlevels`) and the editor test pages bypass the gate on purpose (dev/test access).

Player levels live in localStorage (`hillrunner_custom_v1`) as a grid: `length` columns of `CELL_W`(60)px, each cell `{ h, s?, liquid? }` where `h` is height in `UNIT_H`(25)px units above `BASE_Y`(600) and `null` = pit; obstacles are `{ type, cell, h, params }` from the `OBSTACLE_TYPES` catalog (per-type param ranges/defaults, `span(p)` footprint, `box(p)` selection extents, `pit: true` types carve the ground under themselves). Obstacles anchor at any height row (`ob.h`; older saves without it snap to the nearest ground). `compileCustomLevel()` turns that into the exact shape `LevelBuilder.finish()` emits (chain points sit at column boundaries at the *average* of neighbor heights so staircase paints compile to straight slopes; columns 0–3 and the last two are forced solid for spawn/finish; water/lava/acid runs become `water`/`molten` defs, sludge runs get their own dip chain + `sludge` def), so Terrain/Obstacles/GameScreen consume it unchanged.

**Editor interaction model — deliberately flat.** ONE tray of tools at the bottom, always visible, with the tool you hold *lifted out of the row* (raised, amber-ringed). There is no hidden mode and no configurable hotbar: the old editor had a Terrain/Obstacle mode toggle AND nine assignable slots behind a catalog modal, and "which mode am I in, and what is in slot 4" was the single most confusing thing about it. Groups (Shape / Paint / Build) only decide which row is showing; `Build` also keeps an **All** button that opens the full obstacle grid, because eighteen types don't browse in a one-line scroller. Undo/redo is a JSON snapshot stack (`_snapshot`, 50 deep) taken before every mutation. Placed obstacles can be **dragged** to reposition them: pressing one arms a move, and whether it turns out to be a drag or a tap is decided by whether the pointer travels — so one finger both repositions things and opens their settings, with no modifier and nothing to discover.

**Everything is reachable by touch**, which is the other half of the rewrite. Input is pointer events end to end (one path for mouse/touch/pen): one pointer acts, two pointers pan and pinch-zoom. **Pan and Erase are real tools** pinned beside the group tabs rather than middle-drag and right-click — right-click and middle-drag still work on desktop, but nothing is *only* reachable that way. The subtle one: the first touch of a pinch is indistinguishable from a tap until the second finger lands, so `_ptrDown` marks the edit it starts as pending (`_snapshotPending`) and `_rollback()` undoes it when the second pointer arrives — without that, every two-finger zoom leaves a stray obstacle or a painted column behind. The camera frames the ground inside the band BETWEEN the two chrome strips (`CHROME_TOP`/`CHROME_BOTTOM`), because centring on the raw canvas puts the road behind the tray on a phone.

The chrome is two SLATE strips, not the menus' cream wooden boards: cream vanishes against the Farm's pale sky, and the editor has to stay legible over all six worlds' backdrops. Exactly one control is green — **Test**, the thing you press every thirty seconds. The vehicle chip sits next to it and picks which car a test drive uses (`_test()` passes `vehId` to GameScreen; persisted in `hillrunner_editor_veh_v1`, independent of the garage's active vehicle).

The preview is WYSIWYG: every edit recompiles and rebuilds a parked (never-stepped) `PhysicsWorld`+`Obstacles` and renders with the real set-piece renderer; the placement ghost is a second one-def parked world drawn at half alpha, and tray/catalog icons are the same renderer auto-cropped into data-URLs by `src/ui/ObstacleIcons.js` (its `TWEAKS` map compacts sky-high/road-wide defs for icon legibility only). Camera pans/zooms ease toward `tx/ty/tzoom` targets in `update(dt)`; drags write both for a 1:1 feel. GameScreen plays custom levels via `screens.show('game', { custom: { id, name, theme, level, from }, vehId })` — stars/best-times record under key `custom-<id>`, coins are never paid (farming), and quit/results route back to `from` ('editor' or 'customlevels'). Editor autosaves on exit and before test runs. Deep-links: `?screen=editor&id=<id>&cam=<x>`.

**Infinite mode** — `src/data/infinite.js` + `src/screens/InfiniteGameScreen.js` (extends GameScreen) + `src/screens/InfiniteSelectScreen.js` (reached from the "Infinite" card in the WorldSelect **Extra Modes** section — no longer on Home; screens `infinite`/`infinitegame`; the select screen's back button returns to `worldselect`). The Infinite card is gated by `saveData.isInfiniteModeUnlocked()` (`everyLevelHasStars(1)` — i.e. all worlds completed) and revealed once by the reveal cutscene; per-theme coin unlocks inside the select screen are unchanged. Endless per-theme runs: chunks (~2200px of "features") are generated with the SAME `LevelBuilder` the hand-made levels use (now exported from levels.js) and streamed as paired `Terrain`(+`{ startWall: false }`)/`Obstacles` instances ~4200px ahead of the car, recycled ~2400px behind (the run screen's `level.chains/walls` arrays are live — GameScreen's renderer reads them unchanged; `obstacleSet` is a facade over the chunk list). Each feature lays its own approach/hazard/recovery ground per the spacing rules above, so features never overlap. Open ground between hazards (`terrainRun`) chases a per-run coherent-noise elevation profile (`makeElevation`: multi-octave value noise, per-theme `THEME_TERRAIN` octaves/style — 'smooth' short-step chasing for Farm/Town/Mines/Castle bumpiness, 'terraced' flat-shelves-joined-by-straight-ramps for City/Factory; grades capped under the ~40° friction limit, amplitude eased in over the first ~1km, and the spawn anchor faded out over 5km so runs range BOTH high and low, ~±350px). Terrain dives deep, so `level.deathY` is dynamic (deepest live chunk + 420 — `_updateDeathY`), and a soft-lock watchdog ends the run ("Got stuck!") after 12s at rest with no forward progress — motion of any kind (reversing for a run-up, rocking loose) resets its fuse, so only a car that is genuinely parked burns it. **Fuel is the run's clock**: a tank lasts `FUEL_SECONDS` (32s), red jerry cans spawn on solid ground every `CAN_SPACING_M` (170m, placed per chunk in `_placeCans` — pits are skipped past), touching one refills the tank ("Fuel!" popup), an empty tank ends the run ("Out of gas!"). Collection is a pure distance check in `_trackFuel` — no physics bodies, so the sim never sees it. The HUD (top-left) draws the ⛽ gauge (green→amber→flashing red + a pulsing red vignette under 25%) whenever `_hudExtras` passes `fuel`. Difficulty `difficultyAt(x)` hits 1 at ~1.2km (creeps to 1.6): gaps widen (getting a wooden ramp above ~200px), press/compactor/fireball/rockfall periods shrink, etc. Per-theme feature pools in `THEME_FEATURES`. Economy: `PX_PER_M`=22; crossing a 500m milestone beyond the theme's saved best pays instantly (`milestoneCoins`, × the theme's `payMult`); flips (full airborne rotations) and air time pay at run end. Farm is free; other themes unlock with coins (`saveData.isInfiniteUnlocked`/`unlockInfinite`, best distances in `saveData.data.infinite`). GameScreen's pause-overlay/canvas handlers are guarded with `screens.current === this` because two GameScreen instances now share that DOM. Dev deep-link: `?inf=<themeId>&bot=1&warp=N`. Test page: `test-infinite.html` (generator soak across all themes + a scripted bot run asserting streaming bounds, milestone payout, retry/quit and the unlock flow). Note the Beachday font has no ∞ glyph — spell out "Infinite" in display-font strings.

`test-onboarding.html` guards the first-run coach and the control bindings together (appears once, mirrors the held control, is skippable, retires after driving, never restacks; plus ArrowRight/AZERTY-position bindings, Escape NOT pausing, P/R). Same run style as the other harnesses.

Editor test pages (run like test-sim, need the local server): `test-editor-smoke.html` (compiler + every obstacle type through real physics — no localStorage), `test-editor-drive.html` (bot drives a compiled custom level to WIN), `test-editor-ui.html` (scripted POINTER/DOM interaction suite — covers painting, erasing, undo/redo, obstacle placement and params, two-finger pinch, the test-vehicle pick and the play round trip; asserts land in `<pre id="testlog">`), `test-editor-shot.html` (visual states for `--screenshot`; `&cat=1` opens the obstacle catalog). The UI/shot pages overwrite the custom-level store but stash any real data in `hillrunner_custom_v1_backup` first. Headless quirk: under `--dump-dom` requestAnimationFrame never fires (only timers advance with virtual time; `--screenshot` does drive rAF) — that's why the game's own pages dump empty and the UI test waits on `setTimeout`, and why editor `update()` (dirty-rebuild) only runs under `--screenshot`.

**NEVER put ad-tech words in a filename or URL** (`ad`, `ads`, `advert`, `banner`, `sponsor`, `popup`). The break manager was originally `src/core/AdManager.js` and ad blockers refused to load it — and because a blocked import kills the whole ES module graph, `main.js` never ran and the player got a bare hillside with no menu, on a page with no ads on it. It's invisible to normal debugging: the file serves 200, `fetch()` retrieves it fine (blockers filter by *request type*), and the browser's script error event carries no detail. That's why it's now `src/core/Breaks.js`, and why `test-breaks.html` walks the module graph asserting no URL would trip a blocker. `src/boot-guard.js` also calls this out on screen.

**A dead module graph = a bare hillside, so `src/boot-guard.js` exists** — every menu is DOM built by `main.js` and its imports, so if ANY module 404s, fails to parse, or is blocked (opening `index.html` over `file://`, where browsers refuse ES modules), the player gets sky and grass: no menu, no error. The guard is a CLASSIC script (it has to survive whatever broke the modules), loaded before `main.js` in all three `index.html` copies. It shows the `#boot-error` board (styled in `style.css`): "Serve me over HTTP" on `file://`; otherwise, if `main.js` hasn't set `window.__hillRunnerBooted` within 4 s, it re-walks the import graph with `fetch` and names the file that failed (`/src/core/Platform.js — HTTP 404`), since the browser's own error event carries no detail. `main.js` routes a rejected `boot()` to the same panel via `window.showBootError(title, html)`. **A boot failure must never be a silent blank screen.**

**Engine audio is owned by the run, not the screen.** `sound.startEngine()` lives in `GameScreen._build()` (not `enter()`) because a retry rebuilds without re-entering, and `_win()`/`_fail()`/`_endRun()` call `sound.stopEngine()` outright. `updateEngine(0, false)` only drops the oscillator to idle — it kept humming under the results board.

**Game loop** — single rAF in `src/main.js`; `GameScreen.update` runs a fixed-step accumulator at 60 Hz calling `car.update()` (input + fail checks) before each `physics.step()`. Win = chassis past `level.finishX`; fail = below `level.deathY` or `Car.update` returns `'stuck'` (inverted + genuinely at rest — speed < 0.9, near-zero spin — for a 1.5 s grace window; a flipped car still sliding or being rocked is in motion and must never fail) or `'beached'` (motionless with NO wheel contact while resting on something undrivable — a wall-top perch, a high-center — for 4 s; without it that state is a frozen run, since no wheels = no drive and the chassis touch blocks air control).

**Save data** — one JSON object under `hillrunner_save_v1` behind the `saveData` singleton: coins, per-vehicle upgrades, stars, best times. Reads/writes go through `platform.storage` (localStorage on web/Poki, the account-synced data module on CrazyGames — see Portal builds), so keep the profile ONE serializable object under ONE key. Per-vehicle `upgrades` is the EQUIPPED tier per stat (what physics runs with); `ownedUpgrades` is the highest tier bought — buying is sequential, but any owned tier can be re-equipped from the upgrade screen (no sell-back). Level N unlocks when level N−1 has ≥1 star. New fields must merge over defaults in `load()` so old saves survive. `SaveData` loads once at import (so the test harnesses get a profile) and `main.js` loads it AGAIN after `await platform.init()` — that second load is the one that sees a portal's cloud save.

**Portal builds (CrazyGames / Poki)** — everything portal-specific hides behind `src/core/Platform.js`, whose base version is a no-op with localStorage storage, so the plain web game runs exactly as before. `tools/build-platforms.ps1` copies the game into `builds/crazygames/` and `builds/poki/` (gitignored, `-Zip` for upload-ready archives, dev/test files stripped) and swaps exactly TWO files per build: `index.html` (adds the portal's SDK script) and `src/core/Platform.js` (its SDK guts), both from `tools/platform/<name>/`. **So: never edit `builds/` — fix the base game and re-run the script.** And note the archives: `builds/hillrunner-<name>.zip` is what you actually upload, and it is only rebuilt when you pass `-Zip`. A run without it used to leave a stale archive sitting beside a freshly built folder — the folder looked current while the upload was days old, which is exactly how out-of-date textures reached a portal build. The script now deletes any existing archive when building without `-Zip`, so the two can never disagree. The seam is `init/storage/loadingStart/loadingStop/gameplayStart/gameplayStop/happytime/showAd/watchAudioSetting` plus the `portalAudioControl` flag. **Every build must implement all of it** — `main.js` calls `watchAudioSetting` unconditionally, and a portal Platform.js missing it throws during boot and leaves the player on a bare hillside.

**CrazyGames audio is the SITE's, not the game's.** Their docs are explicit that `SDK.game.settings.muteAudio` outranks any in-game toggle, so that build (a) reads `settings.muteAudio` once and subscribes with `SDK.game.addSettingsChangeListener` to keep it live, and (b) removes the in-game mute control entirely — `#btn-mute` is dropped from its `index.html` (main.js already null-guards it) and `HomeScreen` hides its own toggle whenever `platform.portalAudioControl` is set. Two switches that can disagree is worse than one you don't own. Poki has no such setting, so it keeps the in-game button and stubs `watchAudioSetting`.

**Ads on CrazyGames** use `SDK.ad.requestAd('midgame', { adStarted, adFinished, adError })`. `adError` hands back `{ code, message }`, and `unfilled` / `adblock` / `adCooldown` / `adsDisabledBasicLaunch` are the ORDINARY outcomes of asking — the portal caps midgames at roughly one per three minutes and simply declines in between — so they log at info level and play on rather than reading as faults. `Breaks.js` mutes before the request and unmutes once it settles, which covers the docs' "be silent for the break" rule more completely than muting on `adStarted` would (that leaks engine hum during the request). The watchdog is in TWO stages, and that distinction is load-bearing: one flat timeout fires while a long ad is still on screen, unmuting and unfreezing the game underneath it -- exactly what the docs forbid. A short 15s guard covers a request that never answers at all, and `adStarted` swaps it for a long one once an ad is genuinely playing. `gameplayStart/Stop` are collapsed behind an `_inGameplay` guard because portals reject duplicate/consecutive events and the game fires them from many paths (enter, restart, pause, resume, win, fail, quit), and `showAd()` must never reject — an adblocked or hung ad resolves false so the player still gets their level. `src/core/Breaks.js` (`ads`) owns the cadence: an interstitial every 3 completed levels (`LEVELS_PER_BREAK`), counter advanced ONLY by a win (`noteLevelWon()` in `_win`/`_endRun` — wrecks and retries never march the player toward an ad), taken at the next natural break via `ads.gate(fn)`, which wraps every path back into gameplay (`GameScreen.restart()`, the win screen's Next, the level/theme pickers). During a break `ads.blocking` freezes the rAF loop in `main.js` and `src/ui/AudioBus.js` suspends both AudioContexts (portals require the game paused and silent). `AudioBus` is the ONE audio gate: FOUR independent silencers — ad break, hidden tab (`visibilitychange`; portals reject games that keep sounding in a background tab), the player's persisted mute toggle (`saveData.isMuted()`, surfaced on the home screen and the pause overlay's `#btn-mute`, wired once in `main.js` — test pages boot `main.js` against minimal DOM, so that wiring is null-guarded), and the HOST SITE's own audio setting (`setPortalMuted`, fed by `platform.watchAudioSetting`) — and any one of them suspends both contexts; `Sound`/`Music` consult `isSilenced()` before creating or auto-resuming a context. `main.js` also auto-pauses an in-progress run when the tab hides. Custom/editor levels are exempt from both counter and gate. Test page: `test-breaks.html` (stubs `platform.showAd` and asserts the cadence, the wreck-retry exemption, the freeze/release, adblock recovery, and that no module URL is blocker-bait).

## Physics conventions (the part that will bite you)

- Matter stores velocity in px/step and angular velocity in **radians per 16.6 ms step**, not per second. Vehicle stats are authored in rad/s and converted with `PER_STEP = 1/60` inside `Car.js`. Speeds read off bodies are per-step.
- Screen coords are y-down, so positive angle = clockwise = nose-down for a right-facing car. Gas in air = nose up = **negative** angular velocity.
- Wheel spin alone barely moves the car (the friction solver eats small per-step increments) — propulsion is `Body.applyForce` on the chassis scaled by engine torque, with wheel spin-up layered on for feel/slip. Slopes steeper than ~40° are unclimbable (friction limit); level geometry must respect that.
- Suspension = two spring constraints per wheel anchored at the **chassis top edge**. Anchoring lower makes the triangle bistable — wheels flip above the chassis on hard landings. Don't "simplify" the anchor points.
- Grounded state comes from collision events (`PhysicsWorld` stamps `body.plugin.lastContact`), not raycasts. A wheel counts as grounded for 90 ms after its last terrain contact.
- Terrain chains become thin rotated static rectangles offset half a thickness below the surface line; walls/beams are plain static rects. Every drivable surface — including *dynamic* obstacle planks (seesaw, rope bridge) — is labeled `'terrain'`, because grounded/stuck detection keys on that label.
- Seesaw planks must spawn pre-tilted with the approach end on the ground (Obstacles.js does this); a horizontal plank presents its edge at bumper height and hard-stops the car.
- Tree canopies are `isSensor` bodies labeled `'canopy'`; `Car.update` bleeds ~10%/step of velocity while overlapping one and suppresses the stuck-fail timer (a snagged car always drops out). Place canopies so the drop-out point is solid ground, not a pit — snags should slow, not kill.
- Sensor zones generalize the canopy trick: `PhysicsWorld` stamps `plugin.last<Zone>` + `plugin.zone<Zone>` on wheels/chassis for labels `canopy`/`oil`/`updraft`/`water`; `Car.update` applies the effect (oil = signed horizontal shove from the zone's `plugin.push`; updraft = lift capped at a ~3.5 px/step terminal rise rate and tilted 30% forward — both caps prevent a slow car being tossed sky-high or hovering forever; water = heavy drag, then a `'sank'` verdict after 0.55 s submerged, so fast skims survive).
- Ballistic arcs bleed forward speed fast (chassis `frictionAir` 0.01/step ⇒ ~2 s airborne loses ~2/3 of vx), so a car launched too high lands nearly vertically. Never stack a ramp AND a fan on the same gap, and keep water/pits out of the far landing zone of any big-air feature; conversely a fan inside a gap is a good rescue for undershot jumps since the cap makes it gentle.
- Wrecking balls (and Castle's short-chain `spikyBall()` flails) are **driven** pendulums, not free ones: a mover writes the analytic swing `angle0*cos(2*pi*t/T)` — position, velocity and angle — every step, so the rate and the amplitude are dead constant for the whole run. A free Matter pendulum bleeds energy through the constraint solver and through every car it clips, and a ball that quietly stops reaching the road turns a timing puzzle into a dead prop. `T` defaults to the natural period of a pendulum that length (`pendulumPeriod()`), so it still LOOKS right; flails run at 0.78x that. The body stays dynamic (label `'ball'`, not terrain) so a non-lethal clip still shoves the car. Keep other set-pieces out of the swing arc (±len·sin(angle0) around the anchor).
- Ball lethality is **closing speed** (`ballStrike` in PhysicsWorld): the rate the gap between ball and car is shutting, counting BOTH bodies' motion, over 4.5 px/step. So it kills whether the ball swings into a parked car or the car drives hard into a hanging one — what survives is a low-energy touch. Catching up to a ball swinging away is still safe (the gap is opening), which is deliberate: a car crossing behind a swing outruns the ball and would otherwise die rear-ending it.
- Castle hazards: `fireballPit()` is a `moltenPit` plus a lethal-in-flight sensor fireball (label `'fireball'`, dynamic sensor so terrain never stops it; flight ≈1.9 s of the 3.6 s period — Matter's effective gravity on it is weaker than the ballistic math suggests, so measure, don't derive). `arrowVolley()` looses **real arrows**: one dynamic sensor body per murder-hole (label `'arrow'`, lethal while in flight exactly like rockfall debris), released as a staggered volley from the gallery floor, parked back in the holes once past the road, with spent shafts left stuck in the tarmac behind you. There is no invisible kill box — what you see falling is what kills you. `spikeStrip()` is a thin sensor (label `'spikes'`) → instant `'popped'` verdict. `beam()` is a dynamic terrain-labeled timber, light enough that a good hit topples it and dead enough (restitution ~0) that a hard hit doesn't punt it away.
- **Spike strips go ~25 px past a ramp lip, not further.** A car coming off a ramp leaves nose-UP and sheds forward speed fast (it can exit at 6 px/step even from a maxed car after a slow approach), so it clears a hundred-odd pixels reliably and four hundred not at all. Set further out — or sunk in a pit past the lip — the hazard becomes a coin flip that the most laboured approach always loses. Close in, the launch itself is the answer: a crest launch LANDS on caltrops, a ramp launch flies them. (This was diagnosed with debug-sim; it is not derivable from the ballistic math, because the nose-up attitude is what eats the carry.)
- **A felled beam cannot be used as a bridge.** A 380 px timber takes ~1.5 s to topple; the car covers a 140 px stand-off in 0.15 s, so you always reach the pit before the beam does. Standing it further back buys the time but then it lands nowhere near the pit. The version that works is `barricade()` — a ram wedge with the timber right behind it, so the wedge lifts your nose and the beam goes OVER instead of stopping you dead. A beam standing alone with no approach reads as scenery; the ramp is what makes it a decision.
- Obstacle art is read at 60 km/h for about a second, so these props are drawn as ONE message each and everything else is cut: the tire stack is a springy crown seated in a hollow (its per-tire hubs were invisible and read as gravel), the conveyor is a belt whose drums actually rotate at the belt's own speed (motion that comes out of the mechanism beats a sliding chevron decal), and the oil slick is an iridescent film streaking the way it pushes — warm gold forward for a boost, cold violet-red backward for a shove — with no arrow icons on top, because the sheen IS the signage.
- Arrows park the instant their **tip** reaches the road (`ARROW_TIP`), not once the body is well under it, and spent shafts are drawn with the same `drawArrow()` helper as the ones in flight, clipped at the ground line so the head is buried rather than lying on top of the tarmac. A landed arrow has to be recognisably the object that just went past the windscreen.
- Low overhead structure (`lowBeam()`, and the `underpass`/`dipUnderpass` sections) comes in two looks, chosen per world: `'shed'` is a drive-through farm machine shed rendered as a cutaway and `'gantry'` is a concrete overpass soffit for paved worlds. The shed is **four shapes**: a dark opening, two posts running ground to eave, the header beam, and a red gable roof landing on the post tops. Everything else has been cut, twice. Stopping the posts at the header made the roof read as floating; adding plank seams, corrugated tin and a lit clerestory gap stacked four horizontal bands across the opening and read as a striping glitch. At 60 km/h you see a silhouette and a hole — detail only muddies which edge is the one you have to duck under, so the ONLY thing that pops is the lit strip along the header's underside. Both plant themselves on the road via the wall's recorded `groundY`. The rendered header beam IS the collider rectangle, so the thing you read and the thing that hits you are the same object, and everything else is drawn BEHIND the car: you're threading a low clearance, and foreground structure over the car at that moment is pretty and unplayable.
- **Nothing the car can balance on may be wide, grippy and at car height.** A car that comes down square on a fence top, a wall sill or a shaft-guard ledge sits there with no wheel touching anything — no wheels means no drive, and the chassis contact blocks air control, so the run is frozen (`'beached'` ends it, but that is damage control, not a fix). Rails and guards are therefore 14 px wide at friction ~0.1 (you slide off), and the hole-in-wall's lower half is instead a WIDE block whose top is a drivable ledge you can ride off. Lift and elevator decks span their shaft exactly — an inset deck leaves an edge slot a wheel drops into.
- Falling-scrap chutes drop their chunks as a tight **volley** (bunched into the first fifth of the cycle), not spread evenly across it. Spread evenly, a four-chunk chute rains continuously — each fall takes about as long as the spacing — and the "wait for a clear gap, then commit" read the hazard is built on is never actually available.
- Castle spacing rules (same float logic as the Mines rules below): fireball pits need ~700 px of flat approach (braking must finish short of the lip — parking on it catapults the car); ramp+strip sections need ~1050 px before the next ramp (the launch float carries ~850 past the lip); keep ~1000 px between an arrow volley and the next timing hazard so backing off one doesn't reverse into the other.
- Sensor zones also cover `molten` (lava/acid: near-instant `'melted'` verdict, ~0.12 s grace for a lip graze — no water-style skimming, so `moltenPit()` resumes its far edge `dy` lower; undershooting a level exit would always graze the pool) and `bouncer` (tire stacks: `Car.update` launches the car with vy scaled by landing impact, capped at 16.5 px/step ≈ 390 px rise, tilted slightly forward, 500 ms cooldown). Bouncer contact also counts as ground contact (you can drive on/off a stack).
- **A tire stack throws you off its DECK, never off its flank** — `Car.update` compares the chassis against `bouncer.bounds.min.y`, and only bounces when the car is riding the top. Two things make this the right test and not, say, a minimum impact speed. Firing on *any* contact (the old rule) meant clipping the side of a stack launched you skyward for no visible reason. But gating on impact instead re-opens a worse hole: the bounce firing unconditionally *on top* is what lets a stalled car trampoline out of a tire basin, so an impact threshold leaves a car parked on a stack with no way out and no fail state — a genuine soft-lock. Position separates the two cases cleanly; nothing else does.
- Open water is the harshest gap SHAPE in the game, not the widest: `water()` cuts a level-to-level pit, and banks at equal height mean no fall to buy hang time with. Pass its `dy` to drop the far bank (the `canal()` section does) and it behaves like an ordinary edge jump; leave it level and a 240 px canal drowns cars that clear 400 px pits elsewhere. Sinking is also the one failure a player cannot drive out of, so canals get a long settling flat in front — never enter one while still floating off a fan column or a landing.
- Rockfall debris is lethal only while falling (`label 'debris' && !isStatic`); parked in its chute it's scenery. Ice chains (`surface: 'ice'`) get near-zero friction — no drive, no brakes — so author them flat/downhill with speed carried in, never uphill.
- **Jump sizes are calibrated, not guessed.** Max pit width cleared, pickup, with a realistic (rolling-ground) approach:

  | kind | stock | tier1 | tier2 | tier3 | maxed |
  |---|---|---|---|---|---|
  | cliff edge (`jumpEdge`) | 300 | 250 | 350 | 300 | 350 |
  | launch lip (`jumpGap`)  | 300 | 300 | 450 | 350 | 300 |
  | wooden ramp (`jumpRamp`)| 350 | 500 | 700 | 650 | 550 |

  Regenerate with `/test-jumps.html` (it drives the real sections at every tier) after touching gravity, `DRIVE_FORCE`, the vehicle stat tables or the jump sections, and update this table.

  Two things fall out of this and both drive the level design. First, **the pickup's edge/lip ceiling is ~300 px at EVERY tier** — a very fast car floats off a launch crest and drops into the pit it was aimed over, so more speed genuinely does not buy a wider lip jump. Second, **ramp gaps are the difficulty gate**: 350 (stock) → 500 (tier 1) → 700 (tier 2) is a wide, monotone spread, which is why a 400 px ramp gap is what locks a stock engine out of Farm 7-10. The sports car scales far better than the pickup on every kind (edge 350→600, lip 350→800, ramp 400→800); the bike is the weakest jumper and the best in the air. Landing ramps are sized to the JUMP (`land = 220 + w*0.55`, `run = 60 + w*0.18`) — a fixed short runout turns a cleared gap into a nose-first flip at high tiers.
- Roof-to-roof gaps land FLAT, with no downhill runout to ride the arc out on, so the same width that is comfortable on open ground is a fall up there: keep them ≤ 200 px, step the roofs DOWN across the block, and do NOT put kicker ramps at the edges (a ramp there spends the carry going up instead of across).
- **The float artifact drives Mines-style level spacing:** any hard landing (drop, pit crossing, launch lip) can leave the car "floating" ~100–150 px above the road for ~500 px while the player (or bot) works the air-control, because pumping chassis angular velocity against the spring-mounted wheels sheds most of gravity. This is baked into the tuned feel — design around it, don't "fix" `Car.js`. Consequences: `jumpHole()` teeth sit exactly at float height, so holes need ~550+ px of clean flat approach and must never follow a landing closely; `moltenPit()` must be entered from FLAT road (an up-lip launches fast cars into a long float) and needs its landing float to settle before the next lip; a rockfall pit needs ~600 px of braking room after any jump landing (the bot brakes from `~170 + vx·30` px out, and parking on a crumble bridge or reversing back onto one kills you — keep bridges well outside that window).
- Tire-stack basins: place the stack far enough in (~320 px for a fast entry) that cars falling off the drop edge land ON it, and keep the headwall ~200 px past the stack so the first big bounce clears it; a fast entry that smacks the headwall still recovers by trampolining.
- World gating: `saveData.isWorldUnlocked(id)` requires ≥1 star on the previous world's final level; a world's first level keys off that too.

## Tuning knobs

Feel lives in three places: `engine.gravity.y` in `PhysicsWorld.js`, the stat tables in `vehicles.js`, and `DRIVE_FORCE` / spin-up multipliers in `Car.js`. These have been hand-tuned since the initial build — treat current values as intentional, and rerun `test-sim.html` after changing them (level pass/fail expectations shift with tuning).
